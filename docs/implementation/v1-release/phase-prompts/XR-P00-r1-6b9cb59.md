### 4.2 Wire the five unenforced gates into CI (no owner gate; pre-approved by D-021)

Add the five gates from `E-29` to `.github/workflows/ci.yml`:

| Gate | Command to invoke |
|---|---|
| `placeholder-lint` | `bun run placeholder-lint` |
| `desktop:sink-lint` | `bun run desktop:sink-lint` |
| `ci-capability-gate` | `bun run ci-capability-gate` |
| `website:marketplace:check` | `bun run website:marketplace:check` |
| `changelog:check` | **see D-020 — do not wire blindly** |

Rules:
- Add each new job to **`quality-gate`'s `needs:` list**, otherwise the aggregate passes
  while the new jobs fail (`E-30`). This is the whole point of the item.
- Prefer extending an existing job over adding five new ones where the runtime and
  checkout cost are wasteful (e.g. the cheap static gates can join
  `Architecture (boundaries + size gate)` or `Truth gate`), but **every gate must be
  observable as its own step name** in the run summary. If you consolidate, the step name
  must contain the gate name.
- Do **not** touch `test-e2e-blackbox-proof` or `quarantine` — their exclusion from
  `quality-gate.needs` is intentional (`E-30`).
- Do **not** change any other job's behaviour, runner, timeout or version pins.
- Pin anything new to the same action SHAs already used in the file. Never downgrade an
  action.

**`changelog:check` specifically:** read **D-020**. Because it currently exits 1 at the
baseline, wiring it *as-is* would turn `main` permanently red. Do **not** do that. Choose
**one** and record which:
- **Option A (preferred, D-020a):** produce a real entry via the generator —
  `bun run changelog:generate` — then wire the gate.
- **Option B (D-020b):** wire it only into `release.yml` as a pre-publish gate and leave
  `ci.yml` untouched.
Either way, **`bun run ci` must exit 0 at your final commit** (D-020's invariant). If you
take Option A and the generator rewrites large swathes of `CHANGELOG.md`, stop and report:
that is a release-evidence surface and needs owner review.

### 4.3 A gate-inventory test that prevents recurrence (D-021)

Add a test — `test/architecture/gate-enforcement.test.ts` (or extend an existing file in
`test/architecture/`, whichever the directory's conventions favour — inspect first) —
asserting:

1. For every script name in `package.json` → `scripts.ci`, **either** a workflow invokes
   that script name, **or** a workflow invokes a script that the gate is an alias of,
   **or** the gate is listed in an explicit, commented exemption list with a reason. The
   exemption mechanism must be a small declarative map in the test file, not a silent
   pass.
2. The **aggregate** jobs (`Quality Gate`, and any aggregate that asserts upstreams)
   `needs:` every enforced gate job — so a newly added gate cannot be invisible to the
   aggregate.
3. The test fails for the wrong reason if a gate is removed from `package.json` and
   still referenced — i.e. it also asserts the reverse direction.

Constraints on this test:
- It must be **deterministic and offline** — parse the workflow YAML and `package.json`
  as text/JSON. Do not shell out to `gh`, do not hit the network.
- It must run in the existing `test/architecture/` lane and inside the `unit-tier`
  budget if the directory's lane requires it. If it cannot meet the 5 s unit-tier budget,
  say so and place it in the architecture lane only.
- **Do not** add it to `test/quarantine.json`.
