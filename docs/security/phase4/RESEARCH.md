# XR Phase 4 — Step 3: Research Notes (principles adopted, verified, cited)

Adopted as *principles with sources* — never copied code.

## R1 — Risk-tiered isolation: lightweight OS primitives for frequent/medium risk; microVMs for high/infrequent risk
- **Docker is not a sandbox**: containers share the host kernel; kernel exploits in agent code give host access (T1611 kernel escapes; Langflow CVE-2025-3248 pre-auth RCE as a production example). Use Docker as image format but isolate via Kata/gVisor/microVM for high risk. Source: softwareseni.com AI-agent-sandboxing analysis (2026) [2](https://www.softwareseni.com/ai-agent-sandboxing-explained-why-docker-is-not-enough-and-what-actually-works/).
- **Cold-start trade-offs**: Firecracker ~100–150 ms single-shot / <50 ms prewarmed; gVisor 300–800 ms; Docker 500 ms–2 s; microVM memory overhead 5–15 MB. Source: particula.tech SmolVM/Firecracker/Docker comparison (2026) [1](https://particula.tech/blog/smolvm-vs-firecracker-sandbox-ai-generated-code).
- **Adopted**: Linux medium/high tier = bubblewrap (+seccomp) / raw user namespaces (fast, unprivileged); container runtime when present; gVisor/Firecracker = declared detection hooks (fail-closed when absent; microVM orchestration deferred to Phase 5+, where cold-start budgets matter for high-risk/infrequent actions). macOS = Seatbelt detection stub (documented gap; no macOS runner to validate a profile in this phase).

## R2 — Anthropic sandbox-runtime pattern: OS primitives + domain-allowlist proxy; ~84% permission-prompt reduction
- `sandbox-runtime` (srt) uses Seatbelt on macOS and bubblewrap on Linux with an HTTP/SOCKS5 proxy enforcing a domain allowlist on every child process; Claude Code's `/sandbox` cut permission prompts ~84% in internal testing; auto-allow only *inside* the sandbox; unsandboxed commands still need approval. Sources: rywalker.com research (2026) [1](https://rywalker.com/research/local-agent-sandboxes), inventivehq.com (2026) [2](https://inventivehq.com/knowledge-base/claude/how-to-manage-permissions-and-sandboxing), perrotta.dev (2026) [3](https://perrotta.dev/2026/03/claude-srt-sandbox-runtime/).
- **Adopted**: XR's equivalent = the TrustService environment backends (bwrap/Seatbelt-class) + a **centralized egress proxy** (R4) so the allowlist is enforced at the connection, not merely on tool args. Auto-allow-inside-sandbox maps to XR's approve-once/approval flow (already present); unsandboxed commands map to the fail-closed path.

## R3 — Restrictiveness lattice, escalate-only
- Merge of capability requirements must pick the **more restrictive** placement; agents may escalate isolation, never downgrade (risk tiering is a partial order). Sources: Anthropic sandbox-runtime design [1](https://rywalker.com/research/local-agent-sandboxes) + gVisor/Kata comparisons above (restrictiveness ordering firecracker/kata > gvisor > bwrap > namespace > none) [1](https://particula.tech/blog/smolvm-vs-firecracker-sandbox-ai-generated-code), [2](https://www.softwareseni.com/ai-agent-sandboxing-explained-why-docker-is-not-enough-and-what-actually-works/), [3](https://github.com/NVIDIA/OpenShell/issues/4).
- **Adopted**: `restrictivenessOrder` lattice in `src/runtime/trust/lattice.ts`; `TrustService` keeps a per-run/per-capability escalated tier; every evaluation uses `max(classified, requested, escalated)` — the merge never downgrades.

## R4 — Centralized egress: DNS resolution + private-range/metadata blocking + redirect revalidation + pinning + caps
- Domain allowlists enforced at a proxy on every child process (sandbox-runtime) [1](https://rywalker.com/research/local-agent-sandboxes); credential-injection proxy keeps secrets outside the agent and inspects traffic [1](https://www.penligent.ai/hackinglabs/securing-ai-sre-agents-with-credential-proxies-and-sandboxes/).
- **Adopted**: `src/security/egress-proxy.ts` — WHATWG parse → allowlist → DNS resolve (all A/AAAA) → block any private/link-local/metadata result (RFC1918, 127/8, 169.254/16 incl. 169.254.169.254, ::1, fe80::/10, fc00::/7, 100.64/10, IPv4-mapped) → **connection pinning** (request connects to the pinned resolved address via `lookup` override, `Host`/SNI = hostname) → manual redirects revalidated (max 3) → byte cap + timeout. Metadata/private-range blocking covers the SSRF exfil vector that an arg-level policy check cannot.

## R5 — Credential brokering: secrets outside the sandbox, task-scoped, revocable
- Credential-injection proxy: agent holds *fake* credentials; the proxy substitutes real ones only for approved destinations; keeps reusable secrets outside the agent environment. Tool-broker pattern: agent calls a constrained API; the broker performs the authenticated action outside the agent boundary. Short-lived delegated tokens limit blast radius. Source: penligent.ai (2026) [1](https://www.penligent.ai/hackinglabs/securing-ai-sre-agents-with-credential-proxies-and-sandboxes/); also OS-keychain + tool-injects-directly pattern (secret never in context/logs) [3](https://www.reddit.com/r/AI_Agents/comments/1s7k3qt/secret_proxy_for_agents/).
- **Adopted**: extend the existing `CredentialBroker` (already task-scoped refs + TTL + redaction + `assertClean`): plugin workers bootstrap with **names only**, `secrets.get` is proxied to the main thread (value never persisted/logged/workerData); provider keys stay out of `process.env` on trust paths; children on trust paths get explicit env only.

## R6 — Supply chain: cosign keyless (GitHub OIDC) + SLSA + CycloneDX SBOM + Rekor; `npm ci --ignore-scripts`; trusted publishing; scanning
- Cosign keyless: short-lived Fulcio certs bound to OIDC identity (GitHub Actions), every signature in the append-only public **Rekor** transparency log; verify with `--certificate-identity-regexp` + `--certificate-oidc-issuer=https://token.actions.githubusercontent.com`. SBOM as signed attestation (`cosign attest --type cyclonedx`); SLSA provenance via slsa-github-generator (L3: ephemeral environment, no network, generated provenance); GitHub npm **trusted publishing** (OIDC, no long-lived tokens). Sources: aquilax.ai (2026) [1](https://aquilax.ai/blog/supply-chain-artifact-signing-slsa), kubernetes.recipes (2026) [2](https://kubernetes.recipes/recipes/security/container-image-signing-verification-kubernetes/), oneuptime.com (2026) [3](https://oneuptime.com/blog/post/2026-01-25-cosign-container-image-signing/view).
- **Adopted**: `release.yml` (cosign keyless sign-blob on tarball + SBOM + provenance artifacts; upload to GH Release), `supply-chain.yml` (gitleaks secret scan, SAST/typecheck, dependency vuln scan, license scan, container image scan, SBOM generation), `bun install --frozen-lockfile --ignore-scripts` in CI, npm trusted publishing with `provenance: true`, `scripts/verify-release.ts` + `scripts/sbom.ts` (CycloneDX 1.5 for the locked dep set), local signing verification test with an ephemeral key (Rekor keyless path exercised in CI on first tagged release — documented, not claimed as done).

## R7 — Web/dashboard hardening
- Strict nonce/hash CSP without `unsafe-inline`; HttpOnly/Secure/SameSite cookies; CSRF/Origin checks; rate limits; typed DOM. Sources: standard OWASP guidance (CSRF via SameSite+Origin; CSP nonce/hash; 429 rate limiting) — codified in the Constitution Art. IX recommended practices.
- **Adopted**: T5 implementation (below).

## R8 — Honesty constraints (no claim without evidence)
- Constitution Art. IX.4 / XIX / XXII: no "certified/isolated/signed" without independent evidence; guarantee matrix generated from live probes. SLSA proves *where* built, not that source is safe — combine with scanning + review (aquilax.ai) [1](https://aquilax.ai/blog/supply-chain-artifact-signing-slsa).
