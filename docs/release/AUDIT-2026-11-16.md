## 3 · What is already true at HEAD (do not re-litigate)

1. **The engine↔desktop link is designed and negotiated, not wished into existence.**
   `desktop/src/engine/transport.ts` performs a session-gated handshake on `GET /api/v1/meta/version` and evaluates
   `{contractVersion, minDesktopVersion, schemaVersion, capabilities}` fail-closed (`evaluateEngineContract`):
   missing `contractVersion` ⇒ `legacy` (degraded, reachable, contract unverified); mismatch in either direction ⇒
   typed `incompatible` with actionable copy ("Update the engine" / "Update the desktop app"). The desktop never
   guesses compatibility from the engine's package semver. `desktop/src/engine/diagnostics.ts` produces a redacted,
   allow-listed diagnostics bundle; `desktop/src/components/engine/EngineDownBanner.tsx` implements the full
   five-state vocabulary and shows `starting` silently (bounded by `ENGINE_BOOT_DEADLINE_MS`), `disconnected` only
   after 2 misses, and real actions only (Retry / Start-Restart sidecar / Copy diagnostics / Diagnostics screen).
   The 2-miss latency and the version negotiation were both absent before the `a0d0c45`/`XR-P01`-class work.
2. **Secrets never live in desktop settings.** `saveProviderKeyToEngine` (`desktop/src/engine/providers.ts`)
   `POST /onboarding/provider` writes to the engine's secret broker (OS keychain / Secret Service / DPAPI / encrypted
   file) and returns *metadata* only (backend name, health verdict); the renderer receives no raw key back. The
   provider modal refuses to claim an engine will take a key unless the engine is observed `ready`.
3. **The production bundle carries no demo data.** Seed generators are behind `import.meta.env.DEV` (+
   `VITE_XR_DEMO_DATA=1` for the budget seed); `mock-data-lint` is clean on 500 source files and 79 built chunks;
   `desktop-seed-gate` proves the 7 known seed probes are absent from `desktop/dist`. The shipped auto-purger
   (`desktop/src-tauri/src/seed_purge.rs`) removes legacy seed rows on every open.
4. **The engine owns "which providers exist" and "which are configured."** `GET /api/v1/providers` returns 26 rows
   with `description/docsUrl/baseUrl/authType/keyless/knownModels/hasKey/healthState/checkedAt/latencyMs` (counted by
   executing the gateway offline listing; pinned by `test/providers/offline-listing.test.ts`). S-6 (`2418c60`) made
   Settings → Models derive its configured list from that response. This audit closes the remaining leaks of the same
   two-sources-of-truth pattern.
5. **Voice is engine-first and labelled.** `StepVoice.tsx` previews via engine `/voice/test-tts`; the Web Speech OS
   voice is an explicitly labelled stand-in with pitch mapping; failure modes say so in words; finishing persists Piper
   engine ids verbatim (`piper-kusal` first; gender-guarded by tests).
6. **Version identity is single-sourced, and the MSI mapping is machine-enforced.**
   `src/core/version.ts` is GENERATED from `release.manifest.json` (Article XXII.1): version `1.2.0-preview.1`
   flows to `package.json`, README surfaces, the desktop `"version"` field, updater metadata, and `appMeta.ts`
   (`APP_VERSION = CORE_VERSION`). The WiX `ProductVersion` `1.1.65535.1` is NOT drift — it is exactly
   `msiWixVersion('1.2.0-preview.1')` in `scripts/release-manifest.ts` (semver→MSI down-mapping: pat=0 ⇒
   `maj.(min-1).65535.1`), stamped by `release:stamp` and checked by `release:check`. This audit initially misread
   it as skew (see §6.2 — corrected). `bun run release:check` executed here: **all 10 surfaces in sync at
   `1.2.0-preview.1`**.

## 4 · Root-cause analysis of the four reported issues

### 4.1 · "Install/init shows `not connected to any engine`" (Issue 1)

**Status: root-caused, fixed in-tree, awaiting owner retest. Not reproducible as a code defect at HEAD.**

The exact string does not exist anywhere in the tree (searched twice, including docs). The owner-reported symptom
traces to **T14.b** (`docs/release/WEEK1_LOG.md`, 2026-11-10): the 9e3f703a Linux deb booted, but the packaged
daemon was missing the CORS/preflight response the Linux webview needs for `http://127.0.0.1:<port>/api/*` with
origin `tauri://localhost` — authenticated probes failed before any handler ran, and the UI truthfully reported the
engine as unreachable. Reproduction on the extracted artifact: health 200, but `GET` with `tauri://localhost` origin
returned no `Access-Control-Allow-Origin`, and the `authorization` preflight 404'd. That is why the failure looked
like "XR is broken" rather than "the network policy is wrong".

**Chain of custody after the fix:**

- `a0d0c45` — daemon now answers CORS preflight for the exact native webview origin on `/api/` only, gated on host,
  bearer, and method/header allow-lists; disabled in LAN mode; invalid preflight returns no allow-origin
  (`src/daemon/security-headers.ts`, `src/daemon/server.ts:757-759`). Shell spawns the sidecar with the matching
  `XR_DESKTOP_WEBVIEW_ORIGIN` (`desktop/src-tauri/src/engine.rs` ~L166).
- `desktop/src/engine/transport.ts` + `engineStore.ts` — observed `disconnected` requires two misses; contract
  mismatch is surfaced as `incompatible` with the update path spelled out.
- CI: desktop dispatch `43111084223` and PR `43111087327` passed on `88d381a3`; **installed** Ubuntu 22.04 and
  24.04 webviews authenticated to the app-owned engine, and explicit quit stopped the sidecar; the Windows x64
  journey also passed on that SHA **[ci]**. The matching deb was offered for owner retest.

**Why the user still sees it.** Anyone running a pre-`a0d0c45` installer, a browser preview (no Tauri shell, no
sidecar — `isTauri()` false, no endpoint unless `XR_ENGINE_URL`), or a misconfigured LAN origin will land on the
same words. And on machines where the sidecar cannot spawn (missing/corrupt bundled engine, AV quarantine, port
exhaustion), the banner is *supposed* to say this — with Retry / Start / Copy diagnostics.

**What this audit verified.** Sidecar auth smoke (bearer enforced) passes; banner state machine, diagnostics bundle,
and contract evaluation are as documented above; no init loop re-negotiates on every render (polling is store-owned,
bounded, and independent of route). **No additional code defect found; none changed.**

**Closure condition (out of scope for a code agent):** owner installs the fixed deb on a clean machine, confirms
"engine connected", and Diagnostics shows a `ready` contract with matching versions. Until then T14.b stays OPEN
(`docs/release/PREVIEW1_READINESS.md` — "Owner-installed Linux regression — OPEN").

### 4.2 · Fake / hardcoded data in onboarding and main UI (Issue 2)

**Status: HEAD is mostly clean; three shipping fabrications were found and fixed in this change set.**

The repo's history here is instructive: early builds wrote ~220 spend rows, a 204-row audit chain and three demo
skills into `xr.db` on first launch. All of that is behind the purger (`seed_purge.rs`) and dev-only gates today; the
production bundle is proven clean **[run]** (source lint, bundle lint, seed gate). The T14.b follow-up also removed
scripted demo fallbacks from Brain and Runs and the fabricated tool-trace spawn.

**What still shipped (this audit's F-2, F-3):**

1. **Budget → Models "Test model"** reported success with `Math.random()` latency after ~650 ms and a toast that
   literally admitted "mock round-trip, nothing was charged" (a comment read "Phase 14 wires providers"). This was
   *not* dev-gated — every user saw a fabricated availability probe.
2. **Budget → Models "Download" outside Tauri** slept 900 ms and called `installLocal()`, which marks the model
   installed in desktop settings with zero network or engine I/O. Inside Tauri it at least called `ollamaPull()`, but
   success was inferred from the invoke resolving, never from the engine-side pull stream confirming completion.

**Fixes.** Local "Test model" now performs a real engine round trip (`pingEngineLocalModel('ollama', m.id)`) and
reports observed latency or the observed error verbatim; hosted models get an honest "no live probe exists — spend
tokens or nothing" answer. Downloads in a browser preview fail loudly ("Downloads run in the desktop app") instead of
faking installation; inside Tauri the pull is awaited against the `ollama://pull-progress` event stream and
`installLocal()` is called **only** on `status === 'success'`; an `error` status or a failed stream is surfaced as an
error, never as "ready". Both are pinned by `test/desktop/budget-models-truth.test.ts`.

**Residual, deliberately labelled (not defects):**

- `chatStore` DEV-only "Mock round-trip" — requires `import.meta.env.DEV` and is stripped from production builds.
- `StepVoice` OS stand-in — labelled in copy; engine preview is attempted first.
- `approvalEvents` mock LLM error-rate seam — dev-only via `import.meta.env.DEV`.
- Budget governor’s `configuredModels` / `installedLocal` are desktop-local signals; after this change cloud "configured"
  on the Models tab derives from the engine, and `installedLocal` is only written from engine-confirmed pulls. The
  governor itself remains desktop-local by design (its job is caps before spend, and seeds are purged in prod).
- `brain/demo.ts` — canned run **only** when no provider answers, explicitly labelled "Demo run (no model configured)".

**Onboarding specifically.** Persistence ordering is sound: `finishOnboarding()` writes ONBOARDING_KEY=true only
*after* `prepareModelSetup()` returns, which throws on unconfirmed key save — the All-Set "success" is unreachable on
a failed key write (verified by reading `desktop/src/stores/onboarding.ts` and `src/engine/setup.ts`; additionally
pinned by the new structural test). What was missing was *any statement of what had been verified* on the All-Set
screen (see F-7).

### 4.3 · Model count & OpenAI-compatible API — why does the UI show ~4? (Issue 3)

**Status: no truncation defect exists; the ~4 is a two-sources-of-truth story plus honest availability gating. Fixed at HEAD (S-6) and extended in this change set.**

**The registry (engine).** The engine is the only registry of record:

- `src/providers/presets.ts` → 26 presets (16 hosted + 10 local), each with `defaultModel` and `knownModels`
  (26 defaultModels, 72 knownModels).
- `src/intelligence/capability.ts:modelsFromPreset` builds descriptors:
  `ids = Set([defaultModel, ...knownModels])` per preset; facts come from the one offline register of record
  (`src/core/model-facts.json`, **11 entries**: openai 4, anthropic 4, google 2, ollama 1; version `2026-11-13.1`,
  `staleAt 2027-02-11T00:00:00Z`; enforced by the model-facts gate inside `claim-lint`, wired to a test).
- `src/intelligence/catalog.ts:buildCatalog` (cached, TTL 60 s, stale-while-revalidate 15 s) emits
  **26 providers and 84 model rows** **[run — executed `buildCatalog()` at HEAD: `providers: 26, models: 84`]**.
- Routes: `GET /api/v1/providers` (26 enriched rows), `GET /api/v1/models` / catalog route
  (`src/daemon/routes/providers.routes.ts:168` — returns `modelCount`).

**Any OpenAI-compatible API.** True with an asterisk that matters for procurement: *custom endpoints* are supported
(onboarding and the catalog both carry a `custom` entry, kind `custom`, any base URL), **but** (a) they are
ungoverned — no price facts, no capability claims, `locality: unknown`, labeled as such; (b) the engine refuses
spend it cannot price (price facts ship for openai/anthropic/google only — see
`docs/release/1.2.0-preview.1/known-limitations.md`, "Models and providers"); (c) the SSRF guard refuses loopback
*custom* providers by design (that was the Preview-1 `consumer-smoke` B1 story). "Any OpenAI-compatible API" is
therefore accurate for **text completion over HTTP with a bearer key, without budget enforcement and without factual
model claims** — overselling beyond that is a marketing bug, not a code one.

**Why the user sees ~4.** The Chat model picker (`desktop/src/engine/catalog.ts:modelOptions`) shows a row only
when:

- cloud: `provider.kind !== 'local' && provider.hasKey && registered-in-catalog` (`p.hasKey` comes from the engine —
  no key, no row; the row is not hidden by count anywhere in the tree);
- local: `runtime.discovered && runtime.running && installed.has(model) && registered` — requires the local runtime
  to be running **and** the model installed, i.e. Ollama up with pulled models.

A realistic fresh install (engine up, one cloud key, no Ollama models pulled) shows: that provider's default + its
known models (2–6 rows), zero local rows. "4" is exactly that shape. It is availability, not truncation.

**The real defect underneath (now fixed twice).** Before S-6, Settings → Models listed configured providers from
`settings.models.providers` — written only by its own dialog, initialized `[]` on reinstall, and populated only after
the user clicks "add" — so the engine happily using a key configured three weeks ago rendered as "No providers
configured yet." S-6 (`2418c60`) made the list engine-derived. This audit found and fixed the same class in three
more places (F-1, F-4, F-5): `engineKnowsProvider()` failed **open** with the engine down (a key could be "saved"
for a provider the engine had never heard of), Budget → Models had its own hardcoded 5-entry provider menu, and
both Settings and Budget *write* paths persisted the engine-derived list back into desktop settings.

**Explicitly not a bug:** `catalog.ts` dropping rows whose id is literally `custom` from the *configured* derivation
(the desktop's pseudo-entry id — a pre-existing S-6 dedup; a real custom provider hand-named `custom` in config would
be hidden by it; an operator-chosen id collision, left as-is and flagged here), the 11-fact price register
(intentionally conservative; unknown ≠ free), and the lack of a "show all 84" button — displaying unavailable models
as if selectable would be the dishonest UX. If product wants a browsing surface, the honest version is the "No live
probe for hosted models" pattern already adopted: show everything, label availability. Note also that the measured 84
rows are the built-in presets only; custom endpoints registered in engine config add rows to `buildCatalog()`, so the
live count is "84 + however many customs you registered" — which is exactly the answer to "any OpenAI-compatible
API": the API shape is open, the *governed* truths (price, capabilities) are not, and the UI says so.

**The "27+" claim.** `docs/release/FIXES-2026-11-01.md` §d says "All 27+ engine providers are in the app" — that is
about *providers in the add-catalog* (26 presets + custom = 27), not default models. It is defensible as written.
If marketing wants a model count, the measured one at HEAD is **84 governed rows across 26 providers** — and it will
drift with `PRESETS`; any printed number must be re-measured or generated, never hand-typed.

### 4.4 · Voice AI in onboarding (Issue 4)

**Status: voice path remediated at HEAD (engine-first, labelled stand-in); the *completion predicate* gap is fixed here. Consent capture is still missing (§6.4).**

Verified at HEAD, by reading every screen and the voice engine:

- Preview: `StepVoice.tsx` tries engine `/voice/test-tts` with the selected Piper preset; on engine-unreachable or
  playback failure it falls back to a **labelled** OS Web Speech approximation (pitch-shifted toward the preset) and
  says so in the UI, including "The engine is not reachable, so this preview is your system voice, not XR."
- Persistence: ids chosen in the wizard are engine ids (`piper-kusal`, …) and land verbatim in engine voice settings
  via `applyOnboardingVoice()`; the chosen voice can finish onboarding, reach the engine, and be spoken about
  truthfully. Nothing hard-fails — by design, the wizard must not dead-end on a voice.
- `StepModelSetup.tsx` (not re-audited line-by-line this pass) is the step that can throw on engine-confirmed
  key save, and it routes back to step 4 with a toast instead of claiming success.

**What was missing (fixed here, F-7):** the "You're all set" screen asserted *nothing*. It rendered identical copy
whether the engine was `ready`, `degraded`, or dead — the exact "success predicate" gap AUD-004 names. It now renders
a completion summary from observed state: the persisted model selection (or "Guest mode"), and the engine verdict
("Engine connected and verified." / "…legacy engine, contract not observed." / warning-toned "Engine not reachable…
chat will offer to start it, or open Settings…"). Guest mode remains a legitimate outcome and is labelled as such;
nothing is blocked behind a voice test.

**Not fixed (needs an owner, not a code agent):** versioned terms/privacy acceptance in onboarding. There is no
`TERMS`/`EULA`/`PRIVACY` document anywhere in the tree, `desktop/src` contains zero matches for
`termsAccepted|privacyAccepted|acceptTerms|consentVersion`, and AUD-004 classifies this as release-blocking with the
legal content explicitly parked on decision **D-004** in `docs/implementation/v1-release/DECISIONS.md`. No agent may
invent legal text. The remediation is specified (versioned `{version, acceptedAt}` acceptance step, re-openable from
Settings) — it is deliberately not stubbed here, because a hollow "I accept" checkbox is worse than an honest absence.

## 5 · New defects found this audit — fixed, with tests

All file:line references are against the **modified tree** (this change set). Structural tests live in
`test/desktop/budget-models-truth.test.ts` (15 tests, all passing) and cover the fail-closed, no-fabrication,
no-silent-subset, and completion-honesty properties. The full desktop suite remains green (592/0).

**F-1 · `engineKnowsProvider()` failed open when the engine was down** — `desktop/src/engine/providers.ts:40`
It returned `true` for every id (except `custom`) whenever `GET /providers` had not answered. Consequence: the key-save
pre-flight could assert "the engine will take this key" with no engine, contradicting the very `ready`-only gate two
functions down. Now fails **closed**; the modal copy tells the user exactly what to do ("The engine has not listed this
provider — it may be down, or the endpoint was never registered with it…"). **[fixed · tested]**

**F-2 · Budget → Models "Test model" fabricated latency** — `desktop/src/screens/Budget/components/ModelsTab.tsx` (~L222)
`Math.random()` latency + toast admitting "mock round-trip". Now: local models test through the engine round trip;
hosted models get “No live probe for hosted models” with the honest reason. **[fixed · tested]**

**F-3 · Budget → Models Download silently "installed" models outside Tauri** (~L254-300)
Browser path now errors ("Downloads run in the desktop app…"); Tauri path awaits the `ollama://pull-progress` stream,
calls `installLocal()` only on engine-confirmed `success`, treats `error`/failure as an error toast, and clears state
on every path. **[fixed · tested]**

**F-4 · Budget → Models "Add model" menu was a hardcoded 5-provider subset; cloud "configured" came from a desktop list**
Menu now derives from `buildProviderCatalog(engineProviders)` (26 presets + custom; flagged degraded fallback line
when the engine is unreachable — never silent). Cloud card "configured" now derives from the engine (`hasKey` /
primary), not `settings.configuredModels`. Mirror is mutated only via the local copy (`localMirror`), never by
writing the derived engine list back. **[fixed · tested]**

**F-5 · Settings → Models `saveProvider`/`removeProvider` persisted the engine-derived list** —
`desktop/src/screens/Settings/tabs/ModelsTab.tsx` (`saveProvider` ~L193, `removeProvider` ~L270)
The functions filtered/pushed the *derived* `providers` memo and wrote the result into `settings.models.providers` —
baking engine state (with `addedAt: 0`, `keyStorage: 'engine'`) into desktop settings and dropping mirror entries for
unkeyed providers. Both now operate on the local mirror; removal also gained a `keyStorage: 'none'` branch
("No credential stored for this entry — nothing to remove."). **[fixed · tested]**

**F-6 · Dead default-model controls that silently swallowed user choices (three instances)**
- Settings → Models "Default models" capability selects (chat/coding/embeddings/vision/stt/tts) wrote
  `settings.models.defaults`; **zero readers existed anywhere in the tree** — the choice was remembered and ignored.
  The section is removed with an in-tree comment explaining why (new conversations run on the engine's primary
  provider/model); `CAPABILITIES`/`CapabilityDefaults`/`modelOptions` deleted.
- Settings → General "Default model"/"Fallback model" selects wrote `settings.defaults.model`/`fallbackModel`;
  **zero readers** either (live new-session default = `sessionsStore.resolveDefaultModel()` = cached
  `xr.model.default` → `engineDefaultModel()` → `DEFAULT_MODEL`). Replaced by a pointer row to Settings → Models
  with honest copy. Note the selects also listed *provider ids* where model ids were implied — a second, independent
  dishonesty, now gone.
- `desktop/src/budget/types.ts` comment claimed the budget `defaultModel` "mirrors settings.defaults.model" — no
  such mirror exists; comment corrected (no behavior change).
