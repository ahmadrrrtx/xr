# Desktop shell support matrix — Phase 27

The agent runtime has its own matrix (`SUPPORT_MATRIX.md`, generated from CI
evidence). This one covers the **desktop shell**: tray, global shortcuts,
updater, crash recovery and OS chrome. It exists because the phase brief asks for
polish on three platforms, and "polished" is not a status anyone can check.

**How to read the Status column.** `validated` means a machine ran it and the
evidence is named. `implemented` means the code is complete, compiled and
unit-tested, but the operating-system behaviour itself has not been observed on
that OS. `blocked` means the platform does not offer the hook at all, with the
missing API named. Nothing here is rounded up, and the row that applies to you is
the one to read before believing a feature exists.

Last updated: Phase 27 (`phase/27-shell-polish`), 2026-10-12.

- Rebind, reset-to-defaults and conflict reporting go through
  `shell_shortcut_inventory` / `shell_reset_shortcuts`, so the UI shows what the
  OS actually holds rather than what was requested.
- The HUD keeps its Phase 5 fallback behaviour: the runner-up chord is tried when
  the primary is taken, and the Settings row says which one is live.
- Screenshot-and-ask on Wayland needs `grim` (wlroots), `gnome-screenshot`, or
  the desktop portal; without one the Settings row shows the fix instead of a
  chord that does nothing. `screenshot_ask_support` answers this at runtime.
- Press-and-hold on the PTT chord is registered as a global shortcut with both
  edges reported; the repeat-ignoring logic is the Phase 15 voice controller's,
  unchanged.

## Updater

| State | Behaviour |
| --- | --- |
| Not provisioned (no pubkey in the build) | Every command returns `provisioned: false` with the reason and the operator command. Nothing throws, nothing spins. |
| Dev build | Refuses to run, and says why (there is no installed bundle to replace). |
| Provisioned, up to date | Reports current version and last-check time. |
| Provisioned, update available | Notes, version, date, channel; auto-download fetches on Stable (opt-in on Beta/Nightly). |
| Downloaded | Bytes verified in memory; `readyToInstall: true`; the 36 px banner and the modal offer Install & restart. |
| Install | Signature verified by the plugin's own `download` path; a "later" answer never leaves unverified bytes on disk. |

Channels: `stable` (GitHub `releases/latest`), `beta` and `nightly` (rolling
prerelease tags `updater-beta` / `updater-nightly`), each overridable by the
operator through `plugins.updater.channels`. A prerelease build defaults to its
own channel. Evidence: unit tests in `desktop/src-tauri/src/commands/updates.rs`;
the end-to-end path (a real signed `latest.json`) requires provisioned keys and
is operator-run — see `docs/release/UPDATER.md`.

## What this phase could not verify, and why

1. **Anything that needs a display.** No X server, no Wayland compositor, no
   Windows or macOS GUI in the build environment. Every visual claim above is
   backed by a unit test of the value that drives it (icon filename, tooltip
   string, badge rule, click semantics) or by a rendered mockup — not by a
   screenshot of the real thing.
2. **Traffic-light pixel positions** on macOS. The inset is a documented design
   constant drawn in the renderer and cannot be measured without a Mac.
3. **MSIX install/launch** and **Flatpak build**: both need toolchains absent
   here (`MakeAppx.exe`/`signtool.exe`; `flatpak-builder`). The scripts fail
   loudly rather than producing an unsigned, uninstallable artefact.
4. **Tray rendering on each OS.** The PNG/ICO/icns artefacts are verified
   programmatically (size, format, alpha edges, Template purity, accent
   presence); how a panel actually draws them is a panel question.
5. **A provisioned updater.** Requires the operator's Ed25519 key; the phase
   deliberately ships an inert-but-honest updater rather than a fake endpoint.
