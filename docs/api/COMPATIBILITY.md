# XR Daemon API — Compatibility Policy

**Status:** stable policy (Phase 8) · applies to every daemon route
**Enforced by:** `bun run api:schema:check` (generated schema is fresh),
`bun run api:compat` (no breaking changes vs. the committed contract),
`bun run client:check` (typed client matches the registry) — all three run in CI.

---

## 1. Versioning

All daemon endpoints are mounted **twice**:

| Mount | Status | Header contract |
|---|---|---|
| `/api/v1/…` | **stable, versioned** — the contract | none |
| `/api/…` (unversioned) | **deprecated** legacy twin, sunset **2027-08-01** | `Deprecation: true` · `Sunset: Sun, 01 Aug 2027 00:00:00 GMT` · `Link: <…COMPATIBILITY.md>; rel="deprecation"` |

New integrations MUST target `/api/v1`. The legacy mount exists so existing
dashboards/CLIs keep working through the deprecation window; it is served by
the same handlers and validated by the same schemas (validation responses on
the legacy mount carry the same deprecation headers).

The versioned contract is declared in code (`src/daemon/routes/contract.ts` +
`src/daemon/routes/schemas.ts`, Zod) and **generated**, not hand-written:

- `docs/api/openapi.json` — OpenAPI 3.1 document, generated by
  `bun run api:schema:generate`, freshness-gated by `api:schema:check`.
- `src/clients/daemon-client.generated.ts` — typed fetch client, generated by
  `bun run client:generate`, freshness-gated by `client:check`.

API root discovery: `GET /api` returns the version list, deprecation status,
sunset date, and links to the OpenAPI document. `GET /api/openapi.json`
serves the live document.

## 2. Evolution rules

Per-operation **stability** is declared in the contract (`stable` |
`experimental`) and surfaced in the OpenAPI document.

**Compatible (allowed at any time, no announcement required):**

- adding a new operation;
- adding an **optional** request field;
- adding a response field (request/response schemas are `looseObject`s:
  clients must tolerate unknown fields);
- upgrading stability `experimental → stable`.

**Breaking (requires the deprecation cycle below):**

- removing an operation, or a declared request/response property;
- making an optional request property required;
- narrowing/changing a property's type;
- changing SSE event names or the `ApiError` envelope shape
  (`{ error: { code, message, details? } }`).

`bun run api:compat` diffs the committed OpenAPI document against the live
route registry and **exits non-zero on any breaking finding**. CI blocks the
merge. A genuinely-required breaking change is only shippable by:

1. introducing the replacement under a **new version mount** (`/api/v2`),
   keeping `/api/v1` intact, and
2. announcing the old version's deprecation + sunset (same header pattern
   as the legacy mount), with a documented migration path.

After the sunset date the old version may be removed; removal is recorded in
the changelog and in this document's history section below.

## 3. Deprecation mechanics

A deprecated surface carries, on **every** response (including error and
validation responses):

```
Deprecation: true
Sunset: <HTTP-date>
Link: <https://github.com/ahmadrrrtx/xr/blob/main/docs/api/COMPATIBILITY.md>; rel="deprecation"
```

The sunset window is **≥ 12 months** from deprecation announcement. The
legacy `/api/*` mount was deprecated in Phase 8 (v7.x) with sunset
2027-08-01.

## 4. Error contract

All structured errors use the `ApiError` shape (shared
`#/components/schemas/ApiError`): `{ "error": { "code", "message", "details"? } }`.
Validation failures are `400` with `code: "invalid_request"` and a `details`
array of `{ path, message }` entries. Error *codes* are part of the contract;
error *messages* are not (they may be reworded without notice).

## 5. History

| Date | Change |
|---|---|
| 2026-08 (Phase 8) | `/api/v1` mount introduced; legacy `/api/*` deprecated, sunset 2027-08-01; first generated contract (99 operations) + typed client; breaking-change detection added to CI |
| 2026-08 (Phase 2) | Additive, non-breaking: `GET /api/approvals` (`approvals.list`, stable) lists durable pending approval records across surfaces; `POST /api/approvals/{approvalId}/decision` (`approvals.decide`, stable) approves/denies a pending approval (400 missing `approved`, 404 unknown id, 409 already decided/timed out). Both are served from the same durable consent store as the legacy `/api/control/pending` + `/api/control/approve` pair, which remain for compatibility. TTL default-deny applies: an unanswered approval is denied, never stuck. |
